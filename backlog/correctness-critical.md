# Correctness-critical surfaces

The running register of the **correctness-critical, easy-to-get-subtly-wrong**
pieces that the assertion-first Workflow rule in `CLAUDE.md` applies to: work
where the maintainer writes or tightens the assertion *first* and reviews it, and only
then is the implementation written against it. Rationale and the wider testing
philosophy: `docs/testing.md`.

**This list is non-exhaustive by design, and absence from it proves nothing.**
Deciding whether a given piece of work belongs in this class happens at the
moment the work is done, and that judgement is **Claude's to raise, not
the maintainer's to remember** (the rule says so). A table can seed that judgement and
give us something concrete to point at; it can't replace it, and "it wasn't on
the list" is never a reason to skip the discipline. The counterpart duty: when
new work turns out to be one of these, **add a row here as part of doing it** —
the register only stays useful if it grows with the code.

## Known surfaces

| Piece | Lives in | The subtle way it breaks | Guarded by |
|---|---|---|---|
| Scheduler claim | `server/src/scheduler.js` (`claim`) | double-fire under concurrent ticks; a `next_run_at = $1` equality claim can never re-match the microsecond timestamp Postgres wrote, so the row is silently unclaimable forever | `scheduler-postgres.test.js` (real Postgres — pg-mem's ms timestamps hide this) |
| Slot math | `server/src/schedule.js` | off-by-one at minute / hour / day / weekday boundaries and across DST and timezone; the next slot must land strictly in the future | `schedule.test.js` (pure) |
| Redaction | `agent/redact.py` (`scrub`) | a secret leaks through — inside a URL, as a substring, or because `sensitive` was empty and the guard was wrong | `agent/tests/test_redact.py` (pure) |
| Secret variables (US-035) | `server/src/variables.js` (`resolveForRun`) + the agent `QA_VARS` path | a `secret` variable's value reaches `QA_GOAL`/the persisted `run.goal`/`run.variables` because it was substituted inline instead of routed as a placeholder, or the agent never adds it to `sensitive` so `scrub` can't strip it from frames/steps/report | `variables.test.js` (secret block — value never enters goal/persisted map, routes on `secrets` channel, rejected in start_url) + `agent/tests/test_secret_vars.py` (`QA_VARS` fails closed, loaded secret is scrub-redactable); assertion maintainer-reviewed before implementation |
| Session cookie (US-021) | `server/src/auth.js` (`signSession`/`verifySession`) | a forged or tampered cookie verifies, or an expired one is still accepted — auth becomes decorative, and there is no session table to catch it | `auth.test.js` (round-trip, tamper on every field, forgery without the secret, expiry) — assertion maintainer-reviewed before implementation |
| Magic-link consume (US-021) | `server/src/auth.js` (`consumeLoginToken`) | a link redeemable after use or past expiry = account takeover from anyone who reads a mailbox; a check-then-update consume double-redeems under concurrency | `auth-isolation.test.js` (single-use, expiry, signup-creates-user on pg-mem) + `auth-postgres.test.js` (concurrent double-redeem on real Postgres, which pg-mem can't prove) |
| Per-user API keys (US-021) | `server/src/auth.js` (`mintApiKey`) + `server/src/routes/keys.js` | the plaintext is persisted or handed back on a later read (only the sha256 hash may be stored, shown once at creation); a revoked key still authenticates; a user revokes or lists another tenant's key | `api-keys.test.js` (plaintext-once + hash-only-stored, minted key authenticates as bearer, revoked key refused, cross-tenant revoke 404) — assertion-first, written before the routes |
| Tenant isolation (US-021) | every user-scoped query; `server/src/db.js` (`currentUserId`) routes it | one missed `and user_id = $n` leaks another user's tests, runs, PDFs or recording, and a single-user test DB still returns plausible rows | `auth-isolation.test.js` (list scoping + cross-user test/run/report/recording all 404) — request-scoped `currentUserId()` so a route can't forget to scope |
| Demo run interceptor (US-036) | `server/src/runs.js` (`createRun` demo branch → `startReplay`) | one trigger path (ad-hoc / test / suite / module / schedule / retry) slips past the interceptor and spawns `run_agent.py`, claims a `MAX_CONCURRENT` slot, or calls an LLM — spending the operator's key/box on a stranger via a public, writable endpoint | `demo-interceptor.test.js` (every path: no Python canary, `counts()` stays 0 past the cap, no OPENAI key needed, real owned terminal row, fixture-matched verdict) — assertion-first, reviewed before implementation |
| Demo reaper (US-036) | `server/src/demoReaper.js` (`reapDemoTenants`) | an expired tenant leaves rows or artifact dirs behind: `runs.user_id` is `on delete set null` (`001_init.sql:102`), so a naive user delete orphans run rows and leaks `runs/<id>/` forever — the reaper must rm dirs + delete run rows explicitly, before the user delete | `demo-reaper-postgres.test.js` (real Postgres: completeness across every table incl. runs-by-id + dirs; live/normal untouched; the set-null trap demonstrated) — assertion-first, reviewed before implementation |
| Stored BYOK key (US-005) | `server/src/crypto.js` (`encryptSecret`/`decryptSecret`) + `server/src/openaiKey.js` + `server/src/routes/account.js` | the plaintext OpenAI key is persisted in the clear or handed back on a read (only the AES-GCM ciphertext may be stored, decrypted server-side only to spawn); a tampered ciphertext decodes to attacker bytes instead of failing closed; the resolved run key leaks into `run.goal`/`run.variables`/the persisted row/events/`report_data.json` instead of only the child env; a user reads or clears another tenant's key | `openai-key.test.js` (pure: round-trip, fresh IV, GCM tamper throws, shape gate, request>stored>server precedence) + `openai-key-postgres.test.js` (real Postgres: ciphertext-only at rest, reads never return the value, clear, cross-tenant, run-key containment) — assertion-first, reviewed before implementation |
| Per-user concurrency cap (US-028) | `server/src/runs.js` (`createRun` admission, `canStart`, `startNext` fair-share) + `config.js` | admission counts running-only so a user parks runs in the queue and beats the FIFO; the start-gate/dequeue count running+queued so a scheduled burst that bypassed admission still takes the whole box; a freed slot is promoted FIFO instead of skipping an at-cap user, so one user drains the worker; or the cap leaks into the unset path and stops being byte-for-byte self-host | `concurrency-cap.test.js` (admission counts running+queued, per-user not global, batch partial-accept in order, schedule never rejected) + `concurrency-fairshare.test.js` (schedule bounded to cap running, fair-share at submit + at dequeue — the idle-slot eligibility scan) + `concurrency-off.test.js` (unset = FIFO no-op) — assertion-first, reviewed before implementation |
| Staging/production config separation (US-038) | `docker-compose.prod.yml` (`env_file`, `ports`, the `${COMPOSE_PROJECT_NAME}` labels) + `.env.staging` | a second stack on the same box inherits a production value and stops being staging: `--env-file` feeds interpolation only, so the container still loads `.env` unless `env_file` is overridden — the stack then runs on staging's hostname with production's `SESSION_SECRET`, **live** Stripe keys and real mail recipients. Adjacent variants: a shared secret makes a staging cookie authenticate against production, an un-`!override`n `ports` republishes 5433 so two stacks collide (or the db is exposed), and a duplicated Traefik router name means one hostname silently serves the other's stack | **Candidate — no assertion yet.** Found by rendering `docker compose config` by hand during implementation, which is not a guard. A test can pin it (render both projects, assert the staging service's environment shares no secret value with production's and that neither publishes a port), but it needs Docker in CI, so it waits on US-032. Assertion to be written and reviewed first |
| BYOK-only run funding (US-039) | `server/src/openaiKey.js` (`resolveRunKey`) + `routes/helpers.js` (`requireAgentKey`) + `runs.js` (`startRun`'s child env) + `scheduler.js` | the operator's key funds a stranger's run: one of the run-start paths resolves no key and starts anyway, or — the subtle one — `startRun` spreads `...process.env` into the spawn, so removing the fallback from the expression still lets the server's *ambient* `OPENAI_API_KEY` reach the child, restoring it at the one layer that spends money while every assertion above stays green. Inverse failure: the fallback's removal strands the solo self-hoster, who now has nowhere to put a key (the account router is `authEnabled()`-gated) or no way to store one (`KEY_ENCRYPTION_SECRET` blank) | `byok-only.test.js` (every start path 503s with a live-looking `OPENAI_API_KEY` in the environment — the negative proof that the tier is *gone*, not unconfigured — plus the scheduler's claim-then-skip) + `byok-solo.test.js` (same, auth off) + `byok-postgres.test.js` (real Postgres: the key stores on the seeded operator, every path then starts, the child gets that key and an unfunded run gets none — **pg-mem corrupts `bytea`, so a stored key cannot decrypt there at all**) + `boot.test.js` (`DATABASE_URL`/`KEY_ENCRYPTION_SECRET` refuse to serve when missing) — assertion-first, written and reviewed before implementation |
| Client IP behind the proxy (US-040) | Express `trust proxy` (`TRUST_PROXY` env, default off) → `routes/demoSession.js` (`ipOverQuota`/`recordMint`) + `routes/auth.js`'s magic-link limiter | both directions are a real failure. **Unset** (today): behind Traefik every request's `req.ip` is the proxy container's, so `DEMO_IP_MAX` stops being per-visitor and becomes a **global** cap — the demo greets its sixth visitor of the hour with "too many sandboxes from this address". **Too trusting**: honouring `X-Forwarded-For` on a stack that publishes its port (a plain `docker compose up` self-host) lets any client claim any address and mint past the per-IP cap. The trap is that the test which looks like the guard is the reason it hides: `demo-ip-throttle.test.js` drives the app in-process, where every request really does share one source address, so it passes on a deployment where the throttle is inverted | `trust-proxy.test.js` (the parse: unset/blank/`false`/`off` all trust nothing, a hop count stays a *number*, `true` only by writing it out, garbage never becomes `true`) + `demo-ip-throttle-proxy.test.js` (`TRUST_PROXY=1`: each `X-Forwarded-For` address gets its own quota, and a client-written prefix can't escape the address the proxy appended) + `demo-ip-throttle.test.js` (unset: an invented `X-Forwarded-For` buys nothing) — assertion-first, written before the implementation and confirmed to fail against the shipped code. Found by reading the throttle against the proxy while writing US-040's runbook |
| Billing gates (US-022) | `server/src/billing.js` (`billingReady`/`entitledFrom`/`verifyWebhookSignature`/`claimEvent`/`applySubscriptionEvent`) + `routes/helpers.js` (`requireEntitled`) + the scheduler's fire path | one of the seven run-start paths misses the gate and the paid tier is free through it; or the gate leaks into the `STRIPE_*`-unset path and self-host stops being free; or a forged/replayed/out-of-order webhook grants entitlement — the endpoint is unauthenticated by design, its signature *is* its authentication | `billing-gate.test.js` (every start path refused with no row/slot/spawn, the status table incl. `past_due` either side of `current_period_end` and exactly at it, reads stay open, exempt bypass, schedules claimed-but-not-fired, and — US-051 — that a scheduled `cancel_at` never ends entitlement, asserted past the scheduled instant because reading it there is how a well-meant fix breaks the gate) + `billing-webhook.test.js` (wrong secret, swapped bytes, replay window, 14 malformed headers never 500, stale-event drop, and — US-051 — fixtures in Stripe's *current* API shape, so a reader that looks where the field used to be fails: period end from `items.data[0]` with the top-level location as fallback, `cancel_at` written and cleared) + `billing-webhook-postgres.test.js` (real Postgres: the ledger claim and its concurrent race — pg-mem reports rowCount 1 for a conflicting `on conflict do nothing`, so it would pass an implementation with no idempotency at all) + `billing-off.test.js` (`STRIPE_*` unset = byte-for-byte free) — assertion-first, reviewed before implementation. The UI half of that last claim is `frontend/src/Billing.test.jsx`: no panel, and no `/api/billing` request at all, when `/api/health` reports no `billing` |

| Checkout precondition (US-053) | `server/src/routes/billing.js` (`POST /checkout`) + `server/src/openaiKey.js` (`getUserOpenaiKeyStatus`) | the gate reaches one notch too far and becomes a trap: gating `/portal` locks a lapsed customer out of the card update that would clear the paywall, gating `/status` blanks the screen that says what is missing. The inverse is quieter and costs money — the check runs *after* `createCheckoutSession`, so a refusal has already minted an abandoned Stripe session, or a per-request `openai_api_key` is taken as readiness and sells a subscription to an account with nothing on file | `checkout-key-gate.test.js` (refusal makes no request to a stub Stripe, a body key doesn't satisfy it and isn't stored, exempt refused the same way, and the three things the gate must NOT reach: portal, status, and an existing subscription when the key is later removed) — assertion-first, reviewed before implementation. Note what it deliberately does **not** claim: the key is checked for *shape*, never validated against OpenAI, so "a key is on file" still does not mean "a key that works" |

| Activation window (US-054) | `server/src/activation.js` (`activationStateFrom`/`runGateFor`/`stampActivationRequest`) + `routes/helpers.js` (`requireEntitled`) + the scheduler's fire path + `010_account_activation.sql` | five ways, and only the first is obvious. The gate leaks into the unset path and a self-host — or a billing instance that never set `ACTIVATION_SLA_HOURS` — grows a wall it did not ask for. One of the seven start paths misses it, most likely the scheduler, and the window is bypassable by anyone who saved a schedule before subscribing. An ordinary `customer.subscription.updated` writes over `activated_at` and re-walls a customer who has been running for a month — as does the *migration itself*, on the day the feature is switched on, unless it backfills. The deadline is read from a rewritten timestamp (`updated_at`, or recomputed per event) and slides forward on every webhook, so "24 hours" is unbounded and nothing ever alerts. The script matches an email loosely and activates the wrong account, or two | `activation-gate.test.js` (the window ON: the pure state table incl. off-means-*activated*, all six HTTP paths 503 with `Retry-After` and nothing written, the scheduler's claim-then-skip under its own `pending` counter, reads open, stamped-once across four later events, no webhook path touching `activated_at`, both mails, the five near-miss addresses that must activate nobody, and 010 re-applied over seeded rows) + `billing-gate.test.js` (the window OFF — every fixture user has a null `activated_at`, so that whole file is the regression proof, plus the explicit release of an account left mid-window when the operator turns it off) — assertion-first, written and reviewed before `activation.js` existed. Structural note: the two gates are ONE middleware and one DB read, so a route cannot have the billing check and miss this one |

## What a row owes

A surface listed here should, whenever it is next touched, have its expected
behaviour pinned by an assertion written or tightened **before** the change,
reviewed by the maintainer, and left as the spec the implementation is measured against.
The three built rows above are currently covered test-*alongside* (the tests
shipped with the code); the assertion-first escalation applies to the next
change to any of them. Billing gates were assertion-first from their first
line, as planned: the four test files were written and reviewed before
`billing.js` existed, and writing them first is what surfaced that pg-mem
cannot express the ledger claim at all — a fact that would otherwise have been
discovered by a duplicate charge, not by a test. CRUD and
wiring do not belong here — they stay test-alongside.
